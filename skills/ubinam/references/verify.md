# 确认与证伪

第 6–8 步用。视频里博主最常见的问题不是找不到，而是**确认得太松**：只核两项就宣布（v007）、一条对齐线就说"误差两米"（v006）、打个图钉就算找到（v005）。
AI 的问题更严重：说自己"在地图上量过"其实没量（v010）。本文件的规则是硬性的。

## 1. 看候选之前先写证伪条件

打开卫星图或街景之前，先写 2–3 条"出现就放弃"的条件，例如：
- "路应该在楼的左侧，如果在右侧就排除"
- "远处的山应该在河的对岸，如果在同侧就排除"
- "这里要能拍到日落，镜头朝向必须偏西"

出现就放弃，不找理由圆。确认偏误是这门手艺的头号失败方式：找到一个"看起来对"的地方，就开始给差异找借口。

**证伪条件本身也要核实**，否则会反过来错杀正确答案：
- "从这里看某地标一定在画面里" → 先 `geo.py frame` 算（视角区间、遮挡、像素大小），见 `geometry.md` 第 11 节。
- "线应该在塔上转弯""楼应该有 8 层" 这类从远景推出来的细节 → 没核实就只排序，不排除。
- 用证伪条件排掉的候选记下来；全部候选都没对上时，先回头复查这些条件。

## 2. 比什么、不比什么

| 比（不变特征） | 不比（会变的） |
|---|---|
| 楼的轮廓、层数、窗位和间距、阳台形状 | 停着的车、行人 |
| 电线杆、路灯的位置和数量 | 招牌、广告、遮阳棚（常换） |
| 路缘、围墙拐角、台阶、井盖位置 | 树叶多少、花开没开 |
| 山脊线、河岸线、桥的位置 | 施工围挡、临时设施 |

- **独立**才算数：同一块招牌拍三遍是一项，不是三项。
- 到路：≥2 项独有特征；到楼：≥3 项，并且有两条独立的机位约束。
- "都是黄色瓷砖厂房"这种普遍特征不算独有特征。

## 3. 方位自检（输出前必做）

在卫星图上画出俯视草图：机位 → 前景物 → 中景物 → 远景地标，外加太阳或影子方向。逐项核对：
1. **左右顺序**：照片里 A 在 B 左边，从候选机位看过去也必须是。
2. **远近关系**：照片里 A 挡住 B，候选机位、A、B 必须大致共线且 A 更近。
3. **朝向和太阳**：日落照片镜头必须朝西；从候选点要让画面里的元素同框，镜头只能朝东南，那就不可能是日落（v010-7：AI 选的点只能拍日出，差 850 km）。
4. **视线在路的前方**：车内照片里正前方的塔，必须真的在那条路的前进方向上（v010-4 靠这一条纠正了认错的楼）。
5. **先算方位，再认构件**：照片里的塔、烟囱、楼角对应卫星图上的哪个方块，是没核实的解读。太阳在画面里时用 `sun.py compass --x <构件像素>` 算出它的真实方位，从候选机位沿这个方位去卫星图上找；不要先在卫星图上认定"这个就是塔"再推左右，也不要拿 OSM 建筑轮廓怎么切来判断哪块高——高构件看卫星图上的影子长度和侧墙。认错了会让方位自检把正确的候选错杀。
   卫星图上认高构件：先找一栋确定是竖直的高楼，看能看见它哪一面墙——卫星在那一侧，所有高物体的顶都朝反方向偏；侧墙可见的方块才是高的，塔脚在侧墙底边、影子起点处，不在屋顶投影的中心；影子方向由太阳决定，和倾倒方向不是一回事。两种认法都说得通时，两套机位都画出来，按 `sun.py compass --x` 算的方位各自核对。
6. **方位对不上时先查镜像和日出**：搬运的视频截图常被水平翻转。没有文字时看手势（常用右手）、钟表、车辆驾驶位；候选设施唯一、只有左右对不上时，按"原图 / 镜像""日落 / 日出"建两套模板各核一遍，再决定降档还是扩大搜索。

有一项不过就排除，或者降档并写明原因。

## 4. 没有街景时怎么确认

| 情况 | 替代做法 |
|---|---|
| 山区、郊外、隔江远眺 | `terrain.py view --photo` 渲染候选机位，比山脊轮廓；记住轮廓只证明"在这条视线上"，还要第二条约束。候选多时先批量打分再叠图（`geometry.md` 7.4） |
| 城郊酒店、厂区、景区 | 地图 POI 图片、酒店/景区的网上实拍、游客照片，比天际线上铁塔的塔型、数量、间距（v011） |
| 新建楼盘、商业体 | 房产网楼盘相册（v010-5） |
| 国外 | `mapillary.py near / sheet`（开放许可，多年份）；少量候选再用 `gsv.py near / sheet --headings / render`（官方 Street View Static API，需密钥，只给最新一批，单次 ≤60 张）。题图是 Google 街景截图时，官方接口拿不到同年份批次，比永久结构 |
| 国外乡间、厂区、农场，没有街景 | **先给设施找名字**：OSM 名字、附近地名 + 当地语言的设施类型词（锯木厂 scierie / aserradero 这类）搜网页，新闻、百科、企业官网、博客配图比立面细节（v013 博主就是这样确认的）；再试 Wikimedia Commons 按坐标搜图（免 key，见 `data-sources.md`）；Mapillary 用 `mapillary.py near` 看有没有众包图像；KartaView 覆盖少 |
| 什么地面照片都没有 | 卫星图上 ≥3 项俯视特征唯一对上 + 方位自检通过：片区报高、路报中、楼报低，写明缺实景；不要因为没街景整体退到区县 |

### 沿一条路找门脸

知道路名（新闻稿地址、识图给的街道）但不知道门牌时：

```bash
python3 scripts/osm.py along --bbox <s,w,n,e> --line '["highway"]["name"~"<路名片段>"]' --step 120 --out pts.json --proxy socks5h://127.0.0.1:10808
python3 scripts/mapillary.py sheet --panos imgs.json --toward <lat,lon> --out road.jpg      # 或 gsv.py sheet --points pts.json --headings 30,90（≤60 张）；国内换 baidu_pano.py
```

- 间距 ≤150 m：门脸只在很窄的角度里看得见，400 m 间距容易一家都扫不到。
- 朝向按"行驶方向 + 店在哪一侧"定：靠右行驶的国家、车内拍右侧的店，北行时取 20–90°。复现车内仰拍门脸的构图加 `--pitch 15–20`。
- 找路边的厂房、田块用卫星缩略图：`--step 300–500 --side <north|south|east|west> --offset <建筑离路的米数>` 再 `tiles.py sheet --zoom 16–17`。

### 视差夹逼定机位

街景已认出同一组地物、但不知道拍摄者在路上哪一点时：

1. 照片里选三个左右排开、远近不同的地物（例：远处楼的边缘、中距离招牌、近处楼的边缘），量出两段像素间距，算比值 r = 左段 / 右段。比值和焦距、裁剪无关，用户拉近拍也能比。
2. 在路上取 2–3 个街景点，朝同一方向看，各量同一个比值；沿路走时比值单调变化，找出把照片比值夹在中间的两个点，按比值插值出机位。
3. 再核一项：照片里各地物的上下遮挡关系（谁在谁前面、谁露出多少）要和插值点一致。
4. 只有一条路时误差主要在“哪条车道”，结论写清车道没定；楼下若还有平行的地面道路，两种都写出来。
5. 没有街景、但三个以上地物能在卫星图上认出坐标时，直接算：`pose.py along spec.json --line <沿拍摄者所在的路画的折线> --step 5`，沿路逐点只解朝向，报最优点和 Δchi2 ≤ 4 的路段；近处有一个地物时区间最窄。验证情况：合成数据（3–4 个地物、6 px 量测误差）找回真值，误差 0–7 m；真实照片待验证，先和手工比值法对照着用。

实测一例：三个街景点的比值 1.29 / 1.5 / 2.5，照片 1.37，机位夹在前两点之间，南北误差约 20–30 m。

### 国内街景的现实

- Google 街景国内基本没有，Google 3D 贴近地面看不出立面；腾讯街景多年未更新；高德没有公开街景接口。
- 百度全景是唯一主力，但只沿市政道路采集：湖边公园步道、校园、小区内部基本没有。拍摄点在这类地方时，用周边道路的全景确认是哪片湖岸、哪栋楼，再用楼的方位（`geo.py bearings`、后方交会）推算步道上的具体位置。
- **百度网页版全景（人工、免费、长期可用）**：浏览器打开 map.baidu.com 搜地名，点右下角“全景”图层，蓝线就是有全景的路段，先看蓝线覆盖再决定去哪些点；点蓝线进入全景，拖动转向，“时光机”可看其他年份。地址栏 hash 里有 panoid、heading，可记录复现，但改 hash 会退出全景，转向要拖动。全景多为沿路行道树视角，水边、园区内部常被遮挡或没有覆盖；先用它确认周边楼和路，别指望在步道上拍到同一视角。网页会按 IP 跳城市、URL 里的缩放常被重置，逐点操作很慢：先在高清卫星图（Esri）上用桥、河道走向、岸线等结构把机位缩到一两处，再只对这几处进全景。河道照片多是站在桥上顺河拍，先数河上的桥、量“远处那座桥”的距离。
- 没有密钥时直说缺什么，给出“能一下分开候选的信息”清单（某栋楼的名字或近照、相册里的拍摄方向、哪个密钥），而不是硬给坐标。

### 同一组照片互相约束

用户给出同一个人、同一次出行的多张照片时，先定位带招牌、能查到名字的几张（门店、商场、医院），得到这组照片的大致范围，再回头查难的那张；难图里的弱线索（某栋楼、某片水）优先在这个范围里找。只用来约束候选，不推断拍摄者的住处（见 README“负责任使用”）。实测一例：餐馆 + 社区服务中心招牌、商厦、服装市场几张先定到同一城区，夜景水面倒影里读出的餐厅名指向一个湖，再在湖边认出湖景照片里的酒店。

### 街景点怎么挑

- 点多时先渲染视野开阔的：水边便道、桥上、路口；Mapillary 按 `date` 挑没被行道树挡住的年份（新图主路常被树挡死）。
- 单点环视：`baidu_pano.py sheet --ids loc:<lat>,<lon> --headings 0,60,120,180,240,300`（国外用 `gsv.py sheet --at` 或 Mapillary 全景）。
- 国内农田、郊野先用 `baidu_pano.py render loc:<lat>,<lon>` 取一两张探有没有全景（灰图 = 没有），再决定要不要成片取图。

## 5. 叠图比对

两张图透视不同时，把原图里的招牌、电杆、窗户裁出来，旋转缩放后贴到街景截图的对应位置，是不是同一个物体一眼可见（v002）。水体、山体轮廓同理：旋转拉伸后叠到卫星图上逐点比（v012）。

```bash
python3 scripts/imgprep.py zoom photo.jpg --box ... --scale 2 --out part.png
python3 scripts/baidu_pano.py render <panoid> --heading 47 --out sv.jpg
python3 scripts/evidence.py spec.json --out evidence.jpg      # 卫星图 + 机位扇形 + 比对格
```

## 6. 历史影像

- 街景比照片早很多年：以老建筑、永久结构为准，新楼可能还没有，标牌可能换过（v003：街景早 10 年，比的是楼和杆）。
- 新建设施（新学校、新厂房）在老街景里还没有：先按日期分组看最新批次，拍到拆迁、围挡、塔吊，就是"这里后来建了东西"的地面佐证，也能给照片定个最早年份。
- 反过来可以给照片定年份：找变化慢的东西（爬藤覆盖范围、树冠大小、围挡、新楼有没有盖起来），在不同年份的街景或卫星图里比，能夹到一两年（v004）。
- 季节看照片里的物候，不看参照街景是几月拍的（v004 博主拿 12 月街景的日期说成"冬天"）。

## 7. 候选城市、候选点多的时候

- 列候选表：一行一个候选，一列一条标准，填"符合 / 不符合 / 看不清"，最后一列写排除理由。
- 候选点一次看一页：`tiles.py sheet --points cands.json --zoom 18`，每格居中、带编号，比在大拼图里找点准（大拼图缩小显示后读像素会偏 50–100 px）。
- 标准只用照片视野内能直接看到的东西。
- 全部过一遍再细看剩下的，不要看到第一个"像的"就停。
- 候选来自 OSM 时，先 `osm.py coverage` 看各候选区的数据量；数据偏少的区不在候选表里不代表不是，单独用 `tiles.py sheet --grid` 扫。

### 找操场（窗景俯拍常见）

1. 从照片读出操场模板：跑道长轴和镜头方向的夹角（横在画面里 ≈ 垂直于镜头方向）、球场和篮球场在跑道哪一侧、近处楼的形状（L 形、口字形）、旁边的空地或坡。
2. 镜头方向来自太阳（`sun.py compass`，没有日期按全年算）或画面里的路、河；两个朝向分不开就两套模板。
3. 先用一张 z16 拼图看城区全貌，颜色鲜亮的新操场一眼可见，像素换坐标用 `tiles.py px2ll`；新老操场都要找全时，候选区县城区铺网格：`tiles.py sheet --grid <城区 s,w,n,e> --zoom 17 --size 320 --cols 5`（一格约 330 m，每页 25 格约 1.5 km × 1.5 km），逐格找红色跑道（被楼影盖住的只露一段弧）。
4. 命中的操场按模板比，再从操场往镜头方向反推机位楼（看得见教学楼哪个侧面、隔着哪条路、俯角多大）。
5. 别默认"跑道横在画面里 = 长轴垂直于视线"：看跑道远边两端哪头更低（更近），斜着的就不垂直；认出 ≥4 个点（跑道弯道、篮球场角、楼角）后用 `pose.py solve` 解朝向和机位，不要手算。

## 8. 出结论前的最后检查

- [ ] 每个"对上了""量过了"都有本次会话里实际产出的文件
- [ ] 误差半径来自交会几何或多项比对，不是拍脑袋的小数位
- [ ] 方位自检四项都过了
- [ ] 找到锚点以后，没有再回到泛化特征去挑别的地方
- [ ] 类别推断列过全部候选，排除理由写了
- [ ] 提示、IP、EXIF 和结论冲突的地方解释了（以画面为准）
- [ ] 关键一步换裁剪或关键词重做过，结果一致
- [ ] 定不到点时写了"已确定到哪一级 + 还缺什么信息"
- [ ] 每一条排除理由都核实过：用"画面里没有 X"排除的算过画框和遮挡；没核实的解读只拿来排序
- [ ] 候选是离散的几个时，选了主答案，没有取中点画大圆
